# DESIGN.md — Events Aggregator

## 1. Назначение проекта

**Events Aggregator** — backend-сервис на Python, который получает мероприятия из Events Provider API, хранит их в PostgreSQL и предоставляет REST API для получения событий, просмотра свободных мест, регистрации и отмены билетов.

Проект разрабатывается в рамках практического задания LMS Portal.

### Основные цели

- Реализовать все обязательные API-контракты из задания.
- Синхронизировать события с внешним сервисом и хранить локальную копию в PostgreSQL.
- Обеспечить корректную работу регистрации и отмены билетов через Events Provider API.
- Покрыть клиент внешнего API, пагинатор и ключевые сценарии тестами.
- Настроить CI/CD с обязательной проверкой Ruff до деплоя.
- Сохранять простую архитектуру без лишних зависимостей и преждевременных абстракций.

### Принцип разработки

**KISS:** использовать минимально достаточные решения. Не добавлять компоненты, которые не нужны для требований задания.

Перед реализацией необходимо провести аудит существующего репозитория. Фактическая структура, конфигурация и уже работающие компоненты имеют приоритет над предположениями в этом документе. Не переписывать существующий код без необходимости.

### Управление зависимостями

- `pyproject.toml` — единственный источник декларации зависимостей и конфигурации инструментов (Ruff, pytest).
- `uv.lock` — фиксирует разрешённые версии; хранится в репозитории.
- `uv` используется для управления зависимостями и воспроизводимой установки (`uv sync --locked`).
- `requirements.txt` **не используется** как второй источник зависимостей. Существующий файл на момент аудита содержит `fastapi` и `uvicorn[standard]` без версий и подлежит удалению при переходе на `uv`.
- Dockerfile устанавливает зависимости через `uv` из `pyproject.toml` и `uv.lock`, а не через `pip install -r requirements.txt`.
- Целевая версия Python — 3.11 (`requires-python` в `pyproject.toml`, базовый образ `python:3.11-slim`). Совместимость с требованиями задания: в проанализированных материалах ограничений на версию Python не обнаружено.

Текущее состояние (на момент аудита): `pyproject.toml` пуст, `uv.lock` отсутствует, Dockerfile использует `pip` и `requirements.txt`. Это целевой подход, а не описание уже сделанного.

Не использовать Celery, Redis, отдельный брокер сообщений или внешнюю систему кэширования: текущие требования не оправдывают их добавление.

## 3. Архитектура приложения

Использовать простую слоистую архитектуру с разделением HTTP API, бизнес-логики, доступа к данным и внешнего API.

### Основные компоненты

1. **API layer** — обработка HTTP-запросов, валидация входных данных, формирование ответов.
2. **Services / use cases** — бизнес-операции, не зависящие от FastAPI и конкретной реализации базы данных.
3. **Repositories** — чтение и запись локальных данных через SQLAlchemy.
4. **EventsProviderClient** — все HTTP-взаимодействия с Events Provider API.
5. **EventsPaginator** — последовательный обход страниц внешнего API.
6. **Sync service** — синхронизация событий, обновление метаданных и обработка ошибок.
7. **Database** — PostgreSQL с моделями SQLAlchemy и миграциями Alembic.

Бизнес-логика не должна самостоятельно выполнять SQL-запросы, создавать HTTP-ответы или зависеть от FastAPI.

API-слой не должен содержать сложную бизнес-логику или самостоятельно обращаться к внешнему сервису.

### Целевая структура (ориентир, не шаблон)

Текущее состояние репозитория: `main.py` в корне, `Dockerfile`, `requirements.txt`, пустой `pyproject.toml`, `.gitignore`, `.github/workflows/deploy.yml`. Остальное ниже — цель.

├── app/                      # пакет приложения; модули добавляются по мере появления функциональности
│   ├── main.py               # приложение FastAPI, lifespan, HTTP-маршруты
│   ├── config.py             # чтение переменных окружения

│   ├── models.py             # модели SQLAlchemy
│   ├── schemas.py            # публичные схемы Pydantic
│   ├── repositories.py       # доступ к PostgreSQL (Repository)
│   ├── events_provider.py    # EventsProviderClient и EventsPaginator
│   └── services.py           # синхронизация, свободные места, регистрация, отмена
├── tests/

├── alembic.ini

Зоны ответственности: HTTP-маршруты и приложение; конфигурация; подключение к БД и модели; репозиторий; клиент Events Provider и пагинатор; бизнес-логика синхронизации и регистрации; тесты. Эти зоны обязательны, а разбиение на файлы — нет: модуль создаётся, когда в нём появляется код. Допустимо, например, держать `EventsPaginator` рядом с клиентом или вынести его в отдельный файл. Не создавать пустые модули и избыточные слои.

Требования задания сохраняются при любой раскладке файлов: Repository pattern для доступа к БД и отсутствие бизнес-логики в HTTP-слое.

Перенос существующего `main.py` в `app/main.py` (с обновлением `CMD` в Dockerfile) — решение этапа реализации; Dockerfile сейчас копирует только `main.py`, и это нужно учесть.

Дополнительные файлы целевого плана (на этапе аудита и корректировки документа не создаются): `.dockerignore` (исключает `.git`, `.venv`, `.idea`, `.env*`, кэши, тесты из образа), `.env.example` без настоящих секретов, `.gitignore` для `.env`, локальных окружений и IDE-файлов (уже существует и покрывает эти случаи).

## 4. Конфигурация и секреты

Все параметры окружения должны читаться из конфигурации приложения.

Не хранить секреты в исходном коде, Dockerfile, GitHub Actions YAML или `DESIGN.md`.

Необходимые настройки:

- `POSTGRES_CONNECTION_STRING` — строка подключения к PostgreSQL, если она предоставляется платформой.
- Либо отдельные `POSTGRES_HOST`, `POSTGRES_PORT`, `POSTGRES_DATABASE_NAME`, `POSTGRES_USERNAME`, `POSTGRES_PASSWORD`, если именно этот вариант предусмотрен существующей конфигурацией LMS.
- `EVENTS_PROVIDER_BASE_URL` — адрес Events Provider API.
- `EVENTS_PROVIDER_API_KEY` — API-ключ внешнего сервиса.
- `SYNC_INTERVAL_SECONDS` — интервал фоновой синхронизации; по умолчанию 86400 секунд.

В первую очередь использовать существующие переменные окружения LMS. Не создавать второй способ настройки подключения к БД, если он не нужен. Какой именно вариант (строка подключения или отдельные переменные) передаёт LMS в контейнер, **не подтверждено**; перечисленные имена — предположение, которое проверяется на этапе подключения БД.

Пример адресов Events Provider:

- Внешний адрес: `http://events-provider.dev-2.python-labs.ru`
- Внутренний адрес кластера: `http://student-system-events-provider-web.student-system-events-provider.svc:8000`

Использовать адрес, соответствующий доступной сетевой конфигурации LMS.

`POSTGRES_CONNECTION_STRING` и `EVENTS_PROVIDER_API_KEY` являются секретами. Не выводить их в логах, тестовых отчётах или диагностических сообщениях.

Файл `.env` не должен попадать в Git. В `.env.example` допустимы только демонстрационные значения без настоящих секретов.

## 5. Модель данных

Использовать PostgreSQL и SQLAlchemy.

**Внешние идентификаторы** (события, площадки, билета) хранятся как строки (`String`/`Text`). Не предполагать, что они UUID: примеры в этом документе (`event-uuid` и т. п.) — условные обозначения, а не подтверждённый формат. После проверки контракта поставщика типы можно уточнить отдельным решением. Внутренние первичные ключи таблиц могут иметь собственный тип, независимый от внешних ID.

**Внутреннее представление и публичный контракт различаются.** Плоские поля в таблицах — деталь хранения; публичный JSON формируется схемами Pydantic (например, вложенный `place`).

### 5.1. Event

Таблица `events` хранит локальную копию мероприятий.

Основные поля:

| Поле | Назначение |
|---|---|
| `id` | Внешний идентификатор события из Events Provider (строка), первичный ключ |
| `name` | Название мероприятия |
| `place_id` | Внешний идентификатор площадки (строка) |
| `place_name` | Название площадки |
| `place_city` | Город |
| `place_address` | Адрес |
| `place_seats_pattern` | Шаблон мест, необходимый для детализации события |
| `event_time` | Дата и время мероприятия |
| `registration_deadline` | Срок регистрации |
| `status` | Статус события |
| `number_of_visitors` | Число зарегистрированных посетителей |
| `changed_at` | Время последнего изменения события у поставщика |
| `created_at` | Время создания события у поставщика |

Типы дат должны поддерживать временные зоны. Для времени использовать `datetime` с корректным сохранением timezone-aware значений.

`place` является вложенным объектом во внешнем API и публичных ответах. **Решение для MVP:** отдельная таблица `places` не создаётся; поля площадки (`place_id`, `place_name`, `place_city`, `place_address`, `place_seats_pattern`) хранятся в таблице `events`. Публичный ответ API собирает из них вложенный объект `place` (`id`, `name`, `city`, `address`, а в деталях события — ещё и `seats_pattern`). Отдельная таблица `places` вводится только при подтверждённой необходимости.

Если поставщик может возвращать `null` для некоторых полей, типы и ограничения должны соответствовать его реальному контракту. Не вводить ограничения, которые не поддерживаются исходными данными.

### 5.2. Ticket

Таблица `tickets` хранит локальные сведения об успешных регистрациях.

Основные поля:

| Поле | Назначение |
|---|---|
| `id` | Внутренний первичный ключ записи |
| `ticket_id` | Внешний идентификатор билета от поставщика (строка), не первичный ключ |
| `event_id` | Внешний идентификатор события, связь с `events.id` |
| `first_name` | Имя зарегистрированного участника |
| `last_name` | Фамилия участника |
| `email` | Электронная почта |
| `seat` | Забронированное место |
| `created_at` | Время локальной регистрации |
| `cancelled_at` | Время отмены; `NULL` — регистрация активна |

Успешная регистрация должна сначала подтверждаться Events Provider API. Локальную запись создавать только после успешного ответа поставщика.

Отмена регистрации выполняется через внешний API. После успешного ответа поставщика в записи выставляется `cancelled_at` (запись не удаляется).

**Решение для MVP:** поставщик может повторно использовать `ticket_id` после отмены, поэтому внешний ID не является единственным неизменяемым идентификатором записи. Уникальность обеспечивается частичным уникальным индексом по `ticket_id` с условием `cancelled_at IS NULL`: среди активных регистраций дубликатов нет, а отменённые записи не мешают повторному использованию ID. Поиск билета при `DELETE /api/tickets/{ticket_id}` выполняется только среди активных записей. Историю изменений и отдельную таблицу аудита не добавлять.

### 5.3. SyncMetadata

Таблица `sync_metadata` хранит состояние синхронизации.

Необходимые поля:

| Поле | Назначение |
|---|---|
| `id` | Идентификатор записи |
| `last_sync_time` | Время последней успешной синхронизации |
| `last_changed_at` | Последнее обработанное время изменения события |
| `sync_status` | Состояние синхронизации |

Для проекта достаточно одной записи состояния синхронизации.

При первом запуске использовать начальную дату `2000-01-01`, если в БД ещё нет сохранённого значения `last_changed_at`.

`last_sync_time` и `last_changed_at` обновляются только после успешного завершения всей синхронизации (см. раздел 8.2).

При ошибке в `sync_status` фиксируется состояние ошибки, подробности пишутся в лог без секретов. Значения `last_changed_at` при этом не меняются. Конкретный набор значений `sync_status` (например, идёт/успех/ошибка) определяется при реализации и не является частью контракта поставщика.

## 6. EventsProviderClient

Весь HTTP-код взаимодействия с Events Provider должен находиться в отдельном классе `EventsProviderClient`.

Компонент отвечает за:

- формирование запросов;
- добавление заголовка `x-api-key`;
- обработку HTTP-статусов;
- таймауты запросов;
- преобразование ответов в данные, пригодные для дальнейшей обработки;
- понятные исключения при сетевых ошибках и ошибках внешнего API.

Не дублировать HTTP-вызовы поставщика в сервисах, API-маршрутах и репозиториях.

Предпочтительно использовать один переиспользуемый экземпляр HTTPX-клиента с корректным управлением временем жизни и закрытием соединений.

Для каждого запроса задавать разумный таймаут. Не использовать бесконечное ожидание.

### Поддерживаемые операции

| Операция | Метод внешнего API |
|---|---|
| Получение страницы событий | `GET /api/events/` |
| Получение свободных мест | `GET /api/events/{event_id}/seats/` |
| Регистрация участника | `POST /api/events/{event_id}/register/` |
| Отмена регистрации | `DELETE /api/events/{event_id}/unregister/` |

Для запросов регистрации и отмены использовать точные имена полей и форматы из контракта поставщика.

Получение событий поддерживает параметр `changed_at`. Поставщик возвращает структуру с `results`, `next` и `previous`.

Согласно заданию, успешная регистрация возвращает HTTP 201 и `ticket_id`, отмена возвращает `{ "success": true }`.

Пути поставщика содержат завершающий слеш, и клиент использует их именно так. Это не относится к маршрутам нашего API (раздел 9).

**Не подтверждено контрактом и проверяется при интеграции:** точные имена и типы полей тела регистрации и отмены, формат ошибок поставщика и коды отказов, полный набор полей события и `place`, допустимые значения статусов.

### Обработка ошибок

- Клиент различает три случая: успешный ответ, HTTP-ошибка (в том числе сетевая ошибка и таймаут) и ошибка разбора данных. Два последних случая приводят к исключению, а не к пустому результату.
- Достаточно небольшого набора исключений: ошибка недоступности/некорректного ответа поставщика и отказ поставщика (с HTTP-статусом и телом ответа для диагностики). Громоздкую иерархию не создавать.
- Сетевые ошибки и таймауты должны приводить к контролируемой ошибке интеграции.
- Ошибки HTTP не должны молча превращаться в пустой список событий.
- Ошибки внешнего API должны быть отделены от ошибок локальной базы данных.
- Не возвращать клиенту необработанные traceback и секретные данные.
- Не добавлять автоматические повторы всех запросов без разбора. Повторять запросы только там, где это безопасно и обосновано.

### Тестирование клиента

Написать pytest-тесты с использованием `unittest.mock` для проверки:

- правильного URL и HTTP-метода;
- заголовка `x-api-key`;
- параметров запроса;
- тела регистрации и отмены;
- успешного разбора ответа;
- обработки HTTP-ошибок;
- обработки таймаутов и сетевых ошибок.

Тесты не должны зависеть от доступности настоящего Events Provider.

## 7. EventsPaginator

`EventsPaginator` отвечает за последовательный обход всех страниц событий поставщика.

Пример использования:

```python
client = EventsProviderClient(...)

for event in EventsPaginator(client, changed_at=cursor):
    # Обработка и сохранение события
    ...
```

Пагинатор должен:

1. Запрашивать первую страницу через `EventsProviderClient`.
2. Передавать `changed_at` при начальном запросе.
3. Получать массив `results`.
4. Возвращать события по одному через итератор.
5. Переходить по URL `next`, пока он не станет `null`.
6. Завершать итерацию после последней страницы.
7. Пробрасывать ошибки клиента (HTTP-ошибка, ошибка разбора) наружу. Ошибка не должна восприниматься как нормальное окончание пагинации.

Не предполагать, что поставщик возвращает фиксированное количество элементов на странице. Не вычислять следующую страницу самостоятельно, если поставщик предоставляет готовый `next`.

Не выполнять HTTP-запросы из API-маршрутов для получения списка событий: пагинатор предназначен для синхронизации.

При тестировании замокировать `EventsProviderClient` через `unittest.mock` и проверить:

- одну страницу;
- несколько страниц;
- пустой результат;
- завершение при `next = null`;
- передачу курсора `changed_at`;
- обработку ошибки клиента.

Не добавлять лишние универсальные механизмы пагинации, если контракт поставщика их не требует.

## 8. Синхронизация событий

Синхронизация должна работать как по расписанию, так и по ручному запросу.

### 8.1. Первичная синхронизация

Если `last_changed_at` ещё не сохранён, использовать `changed_at=2000-01-01`.

Получить все страницы через `EventsPaginator`, обработать события и сохранить их в PostgreSQL.

### 8.2. Последующие синхронизации

Использовать сохранённый `last_changed_at` как исходный курсор следующей синхронизации.

Поставщик принимает дату в формате `YYYY-MM-DD` (по описанию задания; проверяется при интеграции).

Правила курсора:

- Новый `last_changed_at` — это дата `changed_at` (максимум среди) успешно обработанных событий, а не сегодняшняя дата и не время запуска.
- Следующий запрос использует сохранённую дату как есть, **без прибавления одного дня**: события граничной даты будут получены повторно.
- Повторно полученные события обновляются через upsert по внешнему `events.id` и не создают дубликатов.
- Курсор и `last_sync_time` обновляются только после того, как пройдена вся требуемая пагинация и все события сохранены. Курсор не обновляется по частичному результату.
- HTTP-ошибка, ошибка разбора ответа и любая другая ошибка синхронизации не считаются нормальным окончанием пагинации. Курсор остаётся прежним, `sync_status` фиксирует ошибку. Повторный запуск безопасен благодаря upsert.
- Если синхронизация не получила ни одного события, курсор не изменяется.
- Сложную систему восстановления, очереди и распределённые механизмы не добавлять.

**Вопросы контракта поставщика (не считаются подтверждёнными, проверяются при интеграции):** включительна ли граница `changed_at`; в каком часовом поясе и с какой точностью поставщик сравнивает значение; гарантирована ли сортировка результатов; может ли `changed_at` события быть `null`.

### 8.3. Сохранение событий

Для каждого события:

- проверить и преобразовать данные согласно фактическому контракту;
- выполнить вставку либо обновление по внешнему `id`;
- обновить `changed_at` и остальные поля;
- сохранить вложенные данные площадки, необходимые для ответов API.

Операции записи выполнять транзакционно: страница (или вся выборка) сохраняется транзакцией, а обновление метаданных курсора выполняется после сохранения всех событий. При ошибке сохранения не отмечать синхронизацию как успешную и не менять курсор.

### 8.4. Фоновый запуск

Периодическая синхронизация выполняется asyncio-задачей, запускаемой в FastAPI lifespan, один раз в сутки (`SYNC_INTERVAL_SECONDS`, по умолчанию 86400).

При запуске приложения:

- инициализируются необходимые ресурсы (engine, HTTPX-клиент);
- схема БД уже должна быть применена миграциями до старта Uvicorn (раздел 13); приложение не создаёт таблицы само;
- запускается фоновая задача;
- при остановке задача отменяется и дожидается завершения, ресурсы закрываются.

Требования к фоновой задаче:

- Ошибка отдельной синхронизации перехватывается, фиксируется в `sync_metadata` (`sync_status`) и в логах без секретов, курсор не продвигается, цикл продолжается, и следующая попытка выполняется по расписанию.
- Ошибка фонового задания не должна завершать приложение.
- Первый запуск синхронизации не должен блокировать готовность HTTP-сервера (начальный запуск — внутри фоновой задачи). Не блокировать event loop долгими синхронными операциями.
- Конкретное решение о том, запускать ли синхронизацию сразу при старте или через интервал, принимается при реализации; ручной запуск (8.5) в любом случае позволяет получить данные немедленно.

### 8.5. Ручной запуск

`POST /api/sync/trigger` возвращает HTTP 200 (требование задания). **Решение для MVP:** синхронизация выполняется до формирования ответа; переход на HTTP 202 и фоновую постановку не предусмотрен. Это не противоречит фоновой ежедневной задаче: оба пути вызывают одну и ту же функцию синхронизации, различаются только инициатором, а ручной запрос ждёт результата.

Время выполнения синхронизации на реальном поставщике и ограничения таймаута LMS **не подтверждены** и проверяются при интеграции. Если обнаружится фактическая проблема, решение пересматривается отдельно с учётом требований задания.

Защита от параллельного запуска: неблокирующий `threading.Lock` внутри процесса (функция синхронизации блокирующая и выполняется в потоке FastAPI; будущий фоновый worker вызывает её через `asyncio.to_thread`). Если синхронизация уже выполняется, новый запуск не создаёт конкурирующую копию, а ручной запрос получает HTTP 409 (зафиксировано в тестах).

Ограничение: `asyncio.Lock` не защищает от параллельной синхронизации между несколькими процессами или репликами. Решение рассчитано на **одну реплику**; число реплик в LMS — неподтверждённое инфраструктурное допущение. Если оно окажется неверным, решение пересматривается отдельно. Распределённые блокировки (в том числе advisory lock) заранее не добавлять; повторная синхронизация в любом случае безопасна благодаря upsert.

### 8.6. Логирование

Логировать:

- начало и завершение синхронизации;
- количество обработанных событий;
- курсор синхронизации;
- ошибки внешнего API;
- ошибки сохранения;
- длительность операции и статус результата.

Не логировать API-ключи, пароли, строки подключения и персональные данные участников.

## 9. API-контракты

Все маршруты должны быть доступны по указанным путям и использовать согласованные схемы Pydantic.

**Канонический вариант:** маршруты нашего API объявляются **без** завершающего слеша (`/api/events`, `/api/events/{event_id}`, `/api/events/{event_id}/seats`, `/api/tickets`, `/api/tickets/{ticket_id}`, `/api/sync/trigger`, `/api/health`), как в задании.

Корректность API не должна зависеть от неучтённого HTTP 307-редиректа: по умолчанию FastAPI перенаправляет запрос со слешем на путь без слеша (`redirect_slashes`), и клиент автотестов может не следовать редиректу или терять тело запроса. Совместимость с автотестами LMS (запросы со слешем и без него) **необходимо проверить** при реализации; если потребуется, добавляется явный второй маршрут, а не сложная система маршрутизации.

Не путать с Events Provider: у поставщика используются пути с завершающим слешем (раздел 6).

Публичный JSON-контракт определяется заданием и схемами Pydantic независимо от внутренней структуры таблиц.

### 9.1. Health check

`GET /api/health`

Успешный ответ:

- HTTP 200
- JSON:

```json
{
  "status": "ok"
}
```

Этот маршрут должен оставаться простым и не выполнять синхронизацию или тяжёлые запросы к внешнему API.

### 9.2. Ручная синхронизация

`POST /api/sync/trigger`

Успешный ответ — HTTP 200.

Допустимый формат ответа:

```json
{
  "success": true
}
```

Повторный вызов не должен приводить к конкурентной синхронизации.

Ошибки синхронизации должны логироваться и возвращаться в виде корректного HTTP-ответа (при недоступности поставщика — 502 или 503, см. 9.8), а не необработанного traceback.

### 9.3. Список событий

`GET /api/events`

Query-параметры:

| Параметр | Тип | Значение по умолчанию |
|---|---|---|
| `date_from` | дата `YYYY-MM-DD`, необязательная | отсутствует |
| `page` | целое число не меньше 1 | `1` |
| `page_size` | целое число не меньше 1 | `20` |

Получать данные исключительно из локальной PostgreSQL.

Фильтрацию по дате выполнять на уровне SQL. Пагинацию выполнять на уровне SQL, а не после загрузки всех событий в память.

Условие `date_from` применяется к `event_time`: возвращать мероприятия, дата которых не раньше указанной даты. Границы фильтра должны быть явно зафиксированы в тестах.

Формат ответа:

```json
{
  "count": 150,
  "next": "<URL следующей страницы текущего запроса или null>",
  "previous": null,
  "results": [
    {
      "id": "event-uuid",
      "name": "Название мероприятия",
      "place": {
        "id": "place-uuid",
        "name": "Название площадки",
        "city": "Город",
        "address": "Адрес"
      },
      "event_time": "2026-01-11T17:00:00+03:00",
      "registration_deadline": "2026-01-10T17:00:00+03:00",
      "status": "published",
      "number_of_visitors": 5
    }
  ]
}
```

Требования:

- `count` — число всех записей, подходящих под фильтр, до применения пагинации.
- `results` — массив событий текущей страницы, включая пустой массив, если записей нет.
- `next` — ссылка на следующую страницу или `null`, если страница последняя.
- `previous` — ссылка на предыдущую страницу или `null`, если страница первая.
- Ссылки формируются на основе текущего запроса (его URL и параметры `date_from`, `page_size`) и фактических параметров пагинации; фиктивные домены вроде `service.example` не используются. Точный формат URL (абсолютный или относительный) в задании не уточнён и **проверяется по автотестам LMS**; ограничений сверх задания не вводится.
- Каждое событие содержит обязательные поля, ожидаемые автотестами.
- В списке не требуется возвращать `seats_pattern`, если он не предусмотрен контрактом списка.

Порядок результатов должен быть стабильным, например по `event_time` и затем по `id`.

При пустой базе вернуть HTTP 200 с корректной структурой:

```json
{
  "count": 0,
  "next": null,
  "previous": null,
  "results": []
}
```

Пустой список не должен превращаться в `404`.

### 9.4. Детали события

`GET /api/events/{event_id}`

Получать событие из локальной базы данных.

Успешный ответ — HTTP 200:

```json
{
  "id": "event-uuid",
  "name": "Название мероприятия",
  "place": {
    "id": "place-uuid",
    "name": "Название площадки",
    "city": "Город",
    "address": "Адрес",
    "seats_pattern": "A1-1000,B1-2000"
  },
  "event_time": "2026-01-11T17:00:00+03:00",
  "registration_deadline": "2026-01-10T17:00:00+03:00",
  "status": "published",
  "number_of_visitors": 5
}
```

Поле `place.seats_pattern` обязательно для ответа, поскольку его проверяет автотест. Вложенный объект `place` собирается из плоских полей `place_*` таблицы `events` (раздел 5.1). Значения идентификаторов в примерах условны; в реальных ответах это строки, полученные от поставщика.

Если событие отсутствует в локальной базе, вернуть HTTP 404.

Не обращаться к Events Provider для получения деталей при каждом запросе.

### 9.5. Свободные места

`GET /api/events/{event_id}/seats`

Получать актуальные свободные места из Events Provider API.

Успешный ответ — HTTP 200:

```json
{
  "event_id": "event-uuid",
  "available_seats": ["A1", "A3", "A4"]
}
```

Требования:

- `event_id` соответствует запрошенному событию.
- `available_seats` всегда является массивом.
- Использовать in-memory кэш с TTL 30 секунд.
- При попадании в кэш не обращаться к поставщику повторно.
- По истечении TTL получать свежие данные.

Ключ кэша — `event_id`.

Не добавлять Redis или другую инфраструктуру для кэширования.

Если событие отсутствует локально, возвращать HTTP 404. Если внешний API недоступен или вернул некорректный ответ, возвращать контролируемую ошибку интеграции (502 или 503, см. 9.8).

Поведение поставщика для событий в нестандартных статусах (в том числе ошибка вместо списка мест) не подтверждено. Не превращать ошибку поставщика в фиктивный пустой список мест; точное преобразование отказа определяется по фактическому ответу поставщика.

### 9.6. Регистрация билета

`POST /api/tickets`

Тело запроса:

```json
{
  "event_id": "event-uuid",
  "first_name": "Иван",
  "last_name": "Иванов",
  "email": "ivan@example.com",
  "seat": "A15"
}
```

Валидация:

- обязательные поля присутствуют;
- строки не пустые;
- email имеет допустимый формат;
- событие существует локально (иначе 404);
- локальные проверки статуса или срока регистрации допустимы только как предварительные и только если соответствующее правило подтверждено контрактом поставщика или заданием. Закрытый перечень статусов в документе не фиксируется; отсутствующий или неизвестный статус не должен приводить к выдуманному поведению.

**Окончательное решение о возможности регистрации принимает поставщик.** Его отказ обрабатывается и преобразуется в понятный ответ нашего API (см. 9.8).

Бизнес-логика не должна зависеть от конкретного HTTP-фреймворка.

Порядок действий:

1. Проверить данные запроса.
2. Получить событие через репозиторий.
3. Выполнить подтверждённые локальные предварительные проверки (если есть).
4. Выполнить синхронный HTTP-запрос регистрации к Events Provider.
5. При успешном ответе сохранить регистрацию в локальной БД.
6. Вернуть HTTP 201 и идентификатор билета.

Успешный ответ:

```json
{
  "ticket_id": "ticket-uuid"
}
```

Не возвращать HTTP 201 до подтверждения успешной регистрации у поставщика.

Если внешний сервис отклонил регистрацию, не создавать локальную запись успешного билета.

Учесть, что внешний запрос и транзакция PostgreSQL не образуют единую распределённую транзакцию. Не реализовывать сложную компенсационную систему без необходимости, но корректно логировать ошибки сохранения после успешной регистрации у поставщика.

### 9.7. Отмена билета

`DELETE /api/tickets/{ticket_id}`

Порядок действий:

1. Найти активную локальную регистрацию (`cancelled_at IS NULL`) по внешнему `ticket_id`.
2. Определить связанное событие.
3. Вызвать Events Provider API для отмены регистрации.
4. После успешного ответа выставить `cancelled_at` в локальной записи.
5. Вернуть HTTP 200.

Успешный ответ:

```json
{
  "success": true
}
```

При отсутствии активного билета возвращать HTTP 404.

Не сообщать об успешной отмене, если поставщик отклонил запрос.

`ticket_id` — внешний идентификатор, а не первичный ключ: он может повторно использоваться поставщиком после отмены (раздел 5.2).

### 9.8. Преобразование ошибок

Минимальный набор правил:

| Ситуация | Ответ нашего API |
|---|---|
| Поставщик недоступен (сеть, таймаут), отказал (не 2xx) или вернул некорректный ответ | 502 (выбрано при реализации синхронизации, зафиксировано тестами) |
| Неизвестное событие или билет в нашем API | 404 |
| Некорректные входные данные | 422 |
| Отказ поставщика в регистрации или отмене | Статус определяется по фактическому ответу поставщика |

Конкретные коды для конфликтов регистрации (например, занятое место), отмены чужого или несуществующего у поставщика билета и прочих специфичных отказов **не назначаются** до подтверждения ответов поставщика. Ошибки не раскрывают traceback и секреты и не маскируются под пустой результат.

## 10. Бизнес-логика и репозитории

Использовать паттерн Repository для доступа к PostgreSQL.

Минимально необходимы операции для:

- получения события по идентификатору;
- получения списка событий с фильтрами и пагинацией;
- вставки и обновления событий;
- чтения и обновления метаданных синхронизации;
- сохранения регистрации;
- поиска активной регистрации по `ticket_id` и установки `cancelled_at` при отмене.

Сервисы реализуют сценарии:

- синхронизация событий;
- получение свободных мест с кэшированием;
- регистрация билета;
- отмена билета.

Репозитории не должны вызывать Events Provider API.

Бизнес-логика не должна напрямую знать о `HTTPException`, `Request` или других деталях FastAPI.

Допустимо использовать собственные простые исключения для ситуаций, которые API-слой преобразует в соответствующие HTTP-ответы.

Не создавать отдельный класс для каждой функции. Применять абстракции только там, где они упрощают тестирование или разделяют реальные обязанности.

## 11. Тестирование

Использовать pytest.

Тесты должны проверять не только успешные сценарии, но и основные граничные случаи.

### 11.1. Юнит-тесты внешнего клиента

Проверить:

- URL и методы запросов;
- заголовки авторизации;
- параметры и тела запросов;
- успешные ответы;
- HTTP-ошибки;
- таймауты и сетевые исключения.

Использовать `unittest.mock`. Не обращаться к реальному Events Provider во время обычного запуска юнит-тестов.

### 11.2. Юнит-тесты пагинатора

Проверить:

- одну страницу;
- несколько страниц;
- пустой список;
- завершение итерации;
- обработку `next`;
- передачу `changed_at`;
- ошибки клиента.

### 11.3. Тесты API

Проверить:

- `GET /api/health`;
- `POST /api/sync/trigger`;
- `GET /api/events`;
- `GET /api/events/{event_id}`;
- `GET /api/events/{event_id}/seats`;
- `POST /api/tickets`;
- `DELETE /api/tickets/{ticket_id}`.

Проверять HTTP-статусы, структуру JSON, обязательные поля и поведение при отсутствии данных.

### 11.4. Тесты синхронизации

Проверить:

- первую синхронизацию с датой `2000-01-01`;
- инкрементальную синхронизацию;
- обработку нескольких страниц;
- upsert без дубликатов;
- сохранение метаданных;
- обработку ошибок;
- отсутствие продвижения курсора при неуспешном сохранении.

### 11.5. Интеграционные тесты

Если используется тестовая PostgreSQL, проверить репозитории и транзакции на ней.

Не использовать production-базу для тестов.

Юнит-тесты должны быть быстрыми и не зависеть от сети, состояния LMS или реального Events Provider.

### 11.6. Проверка автотестами LMS

Автотесты LMS являются обязательным критерием готовности.

Особое внимание уделить следующей цепочке:

1. Ручной запуск синхронизации возвращает HTTP 200 (автотест допускает 200 или 202; MVP возвращает 200).
2. После ожидания события появляются в `GET /api/events`.
3. Список содержит `count`, `next`, `previous`, `results`.
4. Событие имеет обязательные поля.
5. Детали события возвращают `place.seats_pattern`.
6. Для опубликованного события можно получить свободные места.
7. Успешная регистрация возвращает HTTP 201 и `ticket_id`.
8. Отмена билета возвращает HTTP 200 и `success: true`.

Не считать проверку health check достаточным подтверждением готовности приложения.

## 12. uv и Ruff

Использовать `uv` для управления зависимостями и воспроизводимого окружения.

Зависимости и настройки проекта (Ruff, pytest) определяются в `pyproject.toml` и являются единственным источником (раздел 2). Файл `uv.lock` хранится в репозитории. `requirements.txt` не используется.

Минимальные команды проверки (одинаковы локально и в CI):

```bash
uv sync --locked
uv run ruff check .
uv run ruff format --check .
uv run pytest
```

Проверка форматирования (`ruff format --check`) входит в обязательные проверки CI вместе с линтером.

Не добавлять isort отдельно, если сортировка импортов уже обеспечивается Ruff.

Не отключать правила линтера глобально ради прохождения проверки. Исключения допустимы только при конкретном обосновании.

## 13. PostgreSQL и миграции

Использовать Alembic для управления схемой базы данных.

Миграции должны включать создание необходимых таблиц и индексов.

Предусмотреть индексы для:

- идентификатора события;
- `event_time`, используемого при фильтрации и сортировке;
- `changed_at`, используемого при синхронизации;
- поиска билета по внешнему `ticket_id`: **частичный уникальный индекс** по `tickets.ticket_id` с условием `cancelled_at IS NULL` (раздел 5.2).

Первичный ключ `events.id` (внешний ID) предотвращает дубликаты событий при повторной синхронизации.

Не использовать SQLite в production. SQLite допустим для отдельных простых юнит-тестов, если они не требуют проверки специфичного поведения PostgreSQL. Для проверки транзакций и SQL-особенностей использовать PostgreSQL.

### Запуск миграций

**Решение для MVP:** команда запуска контейнера выполняет `alembic upgrade head`, а затем запускает Uvicorn (например, `sh -c "alembic upgrade head && uvicorn ..."`). Dockerfile при этом меняется на этапе реализации, не сейчас.

Ограничения:

- миграции не выполняются из обработчиков запросов API и из фоновой задачи;
- при принятой конфигурации с одной репликой распределённая блокировка не нужна; число реплик LMS — неподтверждённое допущение (раздел 8.5). Если реплик окажется несколько, способ единовременного запуска миграций пересматривается отдельно, advisory lock заранее не добавляется;
- ошибка подключения к БД или применения миграции при запуске должна быть явной (код возврата и сообщение в логах без строки подключения): контейнер не должен молча стартовать без таблиц. Приложение не объявляется работоспособным, если нужные таблицы недоступны.

Имена переменных подключения к PostgreSQL, которые LMS передаёт в контейнер, **не подтверждены** (раздел 4): используются существующие переменные платформы, второй способ настройки не создаётся.

## 14. CI/CD и деплой

GitHub Actions должен выполнять проверку кода до отправки запроса на деплой в LMS.

### Обязательный порядок (целевой контракт)

Текущий workflow содержит только job `build` и `deploy` без проверок и запускается на push в `main`. Целевая цепочка из трёх job:

1. **`check`**: checkout → установка Python 3.11 → установка uv → `uv sync --locked` → `uv run ruff check .` → `uv run ruff format --check .` → `uv run pytest`.
2. **`build`**: `needs: check`. Сборка и публикация образа в GitHub Container Registry. Выполняется только после успешного `check`.
3. **`deploy`**: `needs: build`. Запрос на деплой в LMS. Выполняется только после успешного `build`.

Ошибка Ruff, проверки форматирования или pytest останавливает последующие job: образ не публикуется и деплой не вызывается.

Сохранить существующие рабочие настройки публикации образа и авторизации в LMS. Не переписывать CI/CD целиком: добавляется job `check` и зависимость `needs`. `.github/workflows/deploy.yml` на этапе корректировки документа не изменяется.

Не подтверждено: успешность текущих запусков workflow, принимаемые LMS коды ответа (сейчас допускается только 200) и доступность используемых версий actions — проверяется по журналу GitHub Actions.

Секреты `LMS_API_KEY` и другие токены должны храниться в GitHub Actions Secrets или в секретах LMS.

Для публикации в GHCR выдавать workflow минимально необходимые разрешения, включая `packages: write`, если это требуется используемой схемой публикации.

### Итеративный деплой

Каждое законченное изменение должно сопровождаться отдельным коммитом и деплоем после прохождения проверок.

Рекомендуемые этапы:

0. Переход на `pyproject.toml`/`uv.lock`/`uv` в Dockerfile, job `check`, `.dockerignore`.
1. Подключение PostgreSQL, модели и миграции.
2. Репозиторий и получение списка событий.
3. Клиент Events Provider и пагинатор.
4. Первичная и инкрементальная синхронизация.
5. Ручной и периодический запуск синхронизации.
6. Детали события и свободные места.
7. Регистрация и отмена билетов.
8. Завершение тестов и проверка CI/CD.

Этапы можно объединять, если это не затрудняет диагностику и проверку изменений. Не накапливать большой объём непроверенного кода до первого следующего деплоя.
