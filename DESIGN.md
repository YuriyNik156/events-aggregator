# DESIGN.md — Events Aggregator

## 1. Назначение проекта

**Events Aggregator** — backend-сервис на Python, который получает мероприятия из Events Provider API, хранит их в PostgreSQL и предоставляет REST API для получения событий, просмотра свободных мест, регистрации и отмены билетов.

Проект разрабатывался в рамках практического задания LMS Portal.

### Статус

Этапы A–D разработки завершены. Подтверждённый результат: **LMS — 8 из 8 автотестов PASSED, 21 октября 2026 года** (раздел 11.6) — для синхронной версии приложения.

После этого приложение **полностью переведено на асинхронный ввод-вывод** (async FastAPI, `httpx.AsyncClient`, SQLAlchemy `AsyncSession` с драйвером `psycopg` в async-режиме, асинхронный фоновый воркер; разделы 3, 6–8, 10). Публичные API-контракты не менялись (OpenAPI-схема сверена с исходной версией и совпадает). Новая версия проверена локальными тестами и интеграционными тестами на реальной PostgreSQL 16 (раздел 11.5); **повторный прогон автотестов LMS после деплоя этой версии ещё не выполнялся**.

### Основные цели

- Реализовать все обязательные API-контракты из задания.
- Синхронизировать события с внешним сервисом и хранить локальную копию в PostgreSQL.
- Обеспечить корректную работу регистрации и отмены билетов через Events Provider API.
- Покрыть клиент внешнего API, пагинатор и ключевые сценарии тестами.
- Настроить CI/CD с обязательной проверкой Ruff до деплоя.
- Сохранять простую архитектуру без лишних зависимостей и преждевременных абстракций.

### Принцип разработки

**KISS:** использовать минимально достаточные решения. Не добавлять компоненты, которые не нужны для требований задания.

Документ описывает **фактическую реализацию**. Источники истины в порядке приоритета: код, модели БД, миграции, схемы и маршруты; тесты проекта; подтверждённые контракты Events Provider из материалов задания; затем сам этот документ. Если документ и код расходятся, исправляется документ, а не работающий код. Рабочие компоненты не переписываются без необходимости.

## 3. Архитектура приложения

Использовать простую слоистую архитектуру с разделением HTTP API, бизнес-логики, доступа к данным и внешнего API.

### Основные компоненты

1. **API layer** — обработка HTTP-запросов, валидация входных данных, формирование ответов.
2. **Services / use cases** — бизнес-операции, не зависящие от FastAPI и конкретной реализации базы данных.
3. **Repositories** — чтение и запись локальных данных через SQLAlchemy.
4. **EventsProviderClient** — все HTTP-взаимодействия с Events Provider API.
5. **EventsPaginator** — последовательный обход страниц внешнего API.
6. **Sync service** — синхронизация событий, обновление метаданных и обработка ошибок.
7. **Database** — PostgreSQL с моделями SQLAlchemy и миграциями Alembic.

Бизнес-логика не должна самостоятельно выполнять SQL-запросы, создавать HTTP-ответы или зависеть от FastAPI.

API-слой не должен содержать сложную бизнес-логику или самостоятельно обращаться к внешнему сервису.

### Асинхронный ввод-вывод

- Все маршруты и все их зависимости объявлены как `async def`. Обычная `def`-зависимость или маршрут FastAPI выполнял бы в пуле потоков (по умолчанию 40) и упирался бы в его размер при медленном поставщике; тест `test_every_route_and_dependency_is_async` обходит маршруты и проверяет это.
- Всё, что ждёт, выполняется через `await`: SQL (`AsyncSession`, `psycopg` в async-режиме), HTTP (`httpx.AsyncClient`), обход страниц (`async for` по `EventsPaginator`).
- `asyncio.to_thread`, потоков и блокирующих сетевых вызовов в рабочем пути нет. Единственный `threading.Lock` — внутри `SeatsCache`: он защищает операции со словарём, внутри которых нет ожидания.
- Результат проверен: 60 запросов, одновременно ждущих медленного поставщика (больше пула потоков и пула соединений), не мешают `GET /api/health` и не держат соединения БД (`tests/test_app.py`, `tests/test_postgres.py`).
- Alembic остаётся синхронным: он запускается до Uvicorn (раздел 13), вне event loop, и использует `get_database_url()` (`postgresql+psycopg`). Приложение использует `get_async_database_url()` — тот же URL с драйвером `postgresql+psycopg_async`; переменные окружения те же.

### Внедрение зависимостей и жизненный цикл

- `get_session` — отдельная `AsyncSession` на каждый запрос (`async_sessionmaker`, `expire_on_commit=False`); после запроса закрывается, незавершённая транзакция откатывается. Одна сессия никогда не используется несколькими задачами.
- `get_provider_client` — **один `EventsProviderClient` (с `httpx.AsyncClient`) на процесс**: `get_shared_client()` создаёт его при первом использовании, им пользуются и маршруты, и воркер; соединения переиспользуются, клиент не закрывается после запроса. Ключ и адрес читаются при создании (смена ключа требует перезапуска). Если `EVENTS_PROVIDER_API_KEY` не задан, маршрут отвечает HTTP 500 «Events Provider is not configured» (без значений секретов), а клиент создаётся при следующем запросе, когда ключ появится.
- `get_seats_cache` — общий для процесса объект `seats_cache`.
- `lifespan` при старте проверяет `PUBLIC_BASE_URL` и `SYNC_INTERVAL_SECONDS` (неверное значение останавливает запуск) и, если интервал не равен 0, создаёт и запускает `SyncWorker` (раздел 8.4). **При остановке:** `SyncWorker.stop()` → закрытие общего клиента (`close_shared_client`) → `dispose_async_engine()`. Клиент и engine закрываются только после того, как задача воркера завершилась; если воркер не удалось остановить даже отменой, они остаются открытыми и пишется предупреждение (процесс всё равно завершается). Если закрытие клиента падает, engine всё равно закрывается.

### Слой сервисов и исключения

Сервисы (`app/services.py`) не зависят от FastAPI: они принимают `AsyncSession`, клиент поставщика и кэш, обращаются к БД через репозитории и сообщают о результатах собственными исключениями (`EventNotFoundError`, `EventNotPublishedError`, `RegistrationClosedError`, `InvalidSeatError`, `SeatUnavailableError`, `RegistrationRejectedError`, `TicketNotSavedError`, `TicketNotFoundError`, `EventStartedError`, `CancellationInProgressError`, `CancellationRejectedError`, `CancellationNotSavedError`, `SyncAlreadyRunningError`, `SyncStoppedError`). Преобразование в HTTP-ответы выполняется только в `main.py`. Репозитории делают `flush`, а `commit`/`rollback` выполняют сервисы.

### Транзакции и соединения

Для каждой операции, обращающейся к поставщику, действует правило **«прочитать → отпустить соединение → вызвать поставщика → записать результат в новой транзакции»**:

| Операция | Последовательность |
|---|---|
| `get_available_seats` | читается событие → `commit` (только возврат соединения) → проверки → кэш или запрос к поставщику |
| `register_ticket` | читается событие (нужные поля сохраняются в локальные переменные) → `commit` → проверки без БД → места (кэш или поставщик) → `register` у поставщика → сброс кэша → **новая транзакция**: `add` + `commit` |
| `cancel_ticket` | защита от повторной отмены → читаются билет и событие → `commit` → проверка начала события → `unregister` у поставщика → сброс кэша → **новая транзакция**: `cancel` + `commit` |
| `sync_events` | **одна транзакция на весь обход**: события и курсор должны сохраниться вместе; в процессе не больше одной синхронизации, значит занято одно соединение |

Зачем: пока медленный поставщик отвечает, транзакция не должна держать соединение пула (по умолчанию 5 + 10); иначе при ~15 одновременных запросах остальные ждали бы свободного соединения, и переход на async ничего бы не дал. Тесты: на SQLite (счётчик пула) и на PostgreSQL (в `pg_stat_activity` нет сессий «idle in transaction» во время вызова поставщика; 40 запросов одновременно ждут поставщика при пуле 15).

Почему это не создаёт новых гонок: приложение не использует `SELECT … FOR UPDATE` и не меняет уровень изоляции, а по умолчанию PostgreSQL работает в `READ COMMITTED` (проверено тестом `test_default_isolation_is_read_committed`), где открытая транзакция чтения не удерживает ни блокировок, ни снимка. Раннее освобождение меняет только время занятости соединения. Поля объектов читаются до `commit`, поэтому сервисы не зависят от `expire_on_commit=False`.

### Отмена задач и неопределённый исход commit

- `asyncio.CancelledError` нигде не поглощается: обработчики откатывают транзакцию (`asyncio.shield`, чтобы откат дошёл до конца) и **перевыбрасывают** отмену.
- **Синхронизация.** Отмена вне `commit` — откат, в логе «cancelled … and rolled back», статус и курсор не меняются (это не ошибка). Если отмена пришла **во время `COMMIT`**, его исход неизвестен: он мог дойти до БД. Тогда лог прямо говорит, что неизвестно, сохранены ли события и курсор; данные при этом согласованы (события и курсор в одной транзакции — либо оба есть, либо обоих нет; проверено на PostgreSQL), а следующая синхронизация начнёт с сохранённого курсора, и upsert делает повтор безопасным.
- **Регистрация и отмена билета.** Отмена задачи до обращения к поставщику или во время ожидания его ответа ничего локально не меняет (исход у поставщика неизвестен, кэш мест не трогается). Отмена **после подтверждения поставщиком, во время локального сохранения** оставляет неизвестным, сохранилось ли это локально: пишется запись уровня ERROR с идентификаторами билета и события (без персональных данных), чтобы расхождение можно было найти вручную; компенсации нет. Отмена задач в обычной работе бывает при остановке сервера; поведение при разрыве соединения клиентом конкретным ASGI-сервером не измерялось.

### Один процесс, одна реплика

Защиты от параллельных операций — **локальные, в памяти процесса**: флаг `_sync_running` («одна синхронизация», общий для ручного и фонового запуска), множество `_cancelling` («одна отмена на билет») и `SeatsCache`. Они корректны, потому что в одном event loop между проверкой и установкой нет `await`. Они **не работают** между процессами и репликами. Поэтому поддерживается только схема «один процесс Uvicorn, одна реплика»: несколько workers Uvicorn или реплик не поддерживаются как гарантия. Что происходит без защиты, показано тестом `test_two_syncs_without_the_guard_never_corrupt_the_data`: две одновременные синхронизации одного нового события — одна завершается ошибкой первичного ключа и откатывается, дубликатов и порчи данных нет, а проигравшая синхронизация записывает статус `error`. Распределённая синхронизация (advisory lock и т. п.) не реализована.

### Локальная разработка и Windows

`psycopg` в async-режиме **не работает на `ProactorEventLoop`**, который Uvicorn использует по умолчанию на Windows: любой маршрут, обращающийся к БД, отвечает HTTP 500 (`InterfaceError: Psycopg cannot use the 'ProactorEventLoop'`); воркер при этом тоже не читает БД. Проверено на реальной PostgreSQL 16. Рабочий способ локального запуска на Windows (проверен: `GET /api/events` → 200 с данными из БД) — запуск сервера в `SelectorEventLoop`:

```python
# только для разработки на Windows; в контейнере (Linux) не нужен
import asyncio

import uvicorn

import main

server = uvicorn.Server(uvicorn.Config(main.app, port=8000, loop="none"))
with asyncio.Runner(loop_factory=asyncio.SelectorEventLoop) as runner:
    runner.run(server.serve())
```

Альтернативы — WSL или Docker (Linux). Runtime-код приложения политику цикла событий не меняет. Тесты на Windows выбирают `SelectorEventLoop` сами (`anyio_backend` в `tests/conftest.py`).

## 4. Конфигурация и секреты

Все параметры окружения должны читаться из конфигурации приложения.

Не хранить секреты в исходном коде, Dockerfile, GitHub Actions YAML или `DESIGN.md`.

Фактически используемые настройки (`app/config.py`):

- `POSTGRES_CONNECTION_STRING` — строка подключения к PostgreSQL; если непуста, имеет приоритет. Драйвер `postgresql`/`postgres` заменяется на `postgresql+psycopg` (его использует Alembic через `get_database_url()`); приложение берёт тот же URL с драйвером `postgresql+psycopg_async` (`get_async_database_url()`). Не-PostgreSQL URL отвергается. Новых переменных окружения для LMS не требуется.
- Иначе используются отдельные `POSTGRES_HOST`, `POSTGRES_PORT`, `POSTGRES_DATABASE_NAME`, `POSTGRES_USERNAME`, `POSTGRES_PASSWORD` (все обязательны; `POSTGRES_PORT` — целое число). Эти же имена использует `alembic/env.py` через ту же функцию конфигурации.
- `EVENTS_PROVIDER_API_KEY` — API-ключ поставщика, обязателен для маршрутов, обращающихся к поставщику.
- `EVENTS_PROVIDER_BASE_URL` — необязателен; по умолчанию `http://events-provider.dev-2.python-labs.ru`.
- `PUBLIC_BASE_URL` — необязателен: внешний адрес сервиса (`https://host[:port]`) для абсолютных ссылок `next`/`previous` (раздел 9.3). Допустимы только схемы `http`/`https`; путь-префикс, учётные данные, query и `#` отвергаются, завершающий `/` отбрасывается. Неверное значение останавливает запуск приложения (проверка в `lifespan`). Для production ожидается `https`; `http` допустим локально, при запуске пишется предупреждение.
- `TEST_DATABASE_URL` — только для тестов: одноразовая PostgreSQL для интеграционных тестов (раздел 11.5). База должна быть локальной, с именем, оканчивающимся на `_test`, и не совпадать с базой приложения; иначе тесты отказываются работать.
- `REQUIRE_POSTGRES_TESTS` — только для CI: если задана, отсутствие `TEST_DATABASE_URL` приводит к ошибке, а не к пропуску PostgreSQL-тестов.

- `SYNC_INTERVAL_SECONDS` — необязателен: интервал фоновой синхронизации в секундах. По умолчанию `86400` (24 часа). `0` отключает фоновую синхронизацию (ручной запуск остаётся). Нецелое или отрицательное значение, а также значение от 1 до 59 — `ConfigError` при старте. Значение больше 86400 допустимо, но пишется предупреждение: требование ежедневной синхронизации тогда не выполняется. Тесты задают `0` автоматически (autouse-фикстура в `tests/conftest.py`).

Ошибки конфигурации (`ConfigError`) не содержат значений секретов. Класс `URL` SQLAlchemy маскирует пароль в `str()`/`repr()`, а `ProviderSettings.api_key` исключён из `repr`.

Пример адресов Events Provider:

- Внешний адрес: `http://events-provider.dev-2.python-labs.ru`
- Внутренний адрес кластера: `http://student-system-events-provider-web.student-system-events-provider.svc:8000`

## 5. Модель данных

Использовать PostgreSQL и SQLAlchemy.

**Внешние идентификаторы** (события, площадки, билета) хранятся как строки (`Text`); значения, пришедшие от поставщика не строкой, приводятся к `str`. Формат идентификаторов (UUID или иной) в материалах не подтверждён, поэтому примеры вроде `event-uuid` в этом документе условны. Внутренние первичные ключи таблиц (`tickets.id`) имеют собственный тип, независимый от внешних ID.

**Внутреннее представление и публичный контракт различаются.** Плоские поля в таблицах — деталь хранения; публичный JSON формируется схемами Pydantic (например, вложенный `place`).

### 5.1. Event

Таблица `events` хранит локальную копию мероприятий.

Основные поля:

| Поле | Назначение |
|---|---|
| `id` | Внешний идентификатор события из Events Provider (строка), первичный ключ |
| `name` | Название мероприятия |
| `place_id` | Внешний идентификатор площадки (строка) |
| `place_name` | Название площадки |
| `place_city` | Город |
| `place_address` | Адрес |
| `place_seats_pattern` | Шаблон мест, необходимый для детализации события |
| `event_time` | Дата и время мероприятия |
| `registration_deadline` | Срок регистрации |
| `status` | Статус события |
| `number_of_visitors` | Число зарегистрированных посетителей |
| `changed_at` | Время последнего изменения события у поставщика |
| `created_at` | Время создания события у поставщика |

Типы дат должны поддерживать временные зоны. Для времени использовать `datetime` с корректным сохранением timezone-aware значений.

`place` является вложенным объектом во внешнем API и публичных ответах. **Решение для MVP:** отдельная таблица `places` не создаётся; поля площадки (`place_id`, `place_name`, `place_city`, `place_address`, `place_seats_pattern`) хранятся в таблице `events`. Публичный ответ API собирает из них вложенный объект `place` (`id`, `name`, `city`, `address`, а в деталях события — ещё и `seats_pattern`). Отдельная таблица `places` вводится только при подтверждённой необходимости.

Допускают `NULL` только `events.registration_deadline`, `tickets.cancelled_at` и поля `sync_metadata` (кроме `id`). Остальные поля `events` обязательны, а число посетителей `null` от поставщика сохраняется как `0` (также `server_default 0`). Внешние ключи: `tickets.event_id → events.id`.

### 5.2. Ticket

Таблица `tickets` хранит локальные сведения об успешных регистрациях.

Основные поля:

| Поле | Назначение |
|---|---|
| `id` | Внутренний первичный ключ записи |
| `ticket_id` | Внешний идентификатор билета от поставщика (строка), не первичный ключ |
| `event_id` | Внешний идентификатор события, связь с `events.id` |
| `first_name` | Имя зарегистрированного участника |
| `last_name` | Фамилия участника |
| `email` | Электронная почта |
| `seat` | Забронированное место |
| `created_at` | Время локальной регистрации |
| `cancelled_at` | Время отмены; `NULL` — регистрация активна |

Локальную запись создаём только после успешного ответа поставщика. Отмена выполняется через внешний API; после успешного ответа в записи выставляется `cancelled_at`, запись **не удаляется** (историческая запись сохраняется).

**Повторное использование `ticket_id`.** Events Provider может выдать тот же `ticket_id` другому пользователю после отмены прежней регистрации (например, когда новый участник занимает освободившееся место). Поэтому:

- `ticket_id` — внешний идентификатор, а не первичный ключ; ключом записи служит внутренний `tickets.id`.
- Глобального `UNIQUE` по `ticket_id` **нет** (и добавлять его нельзя — это противоречило бы контракту поставщика).
- Активность записи определяется условием `cancelled_at IS NULL`.
- Уникальность обеспечивает **частичный уникальный индекс** `uq_tickets_ticket_id_active` по `ticket_id` с условием `cancelled_at IS NULL` (создан миграцией `0001` для PostgreSQL; в модели объявлен также для SQLite, который используется в тестах): среди активных регистраций дубликатов быть не может, а отменённые записи не мешают повторному использованию ID.
- Дополнительный индекс `ix_tickets_event_id` по `event_id`. Уникальности по месту нет: занятость места решает поставщик.
- `TicketRepository.add(**fields)` (все методы репозиториев — `async`) создаёт запись и делает `flush`; `get_active(ticket_id)` ищет запись с `cancelled_at IS NULL` (первую найденную); `cancel(ticket, cancelled_at)` выставляет `cancelled_at` и делает `flush`. Таким образом, после отмены `get_active` возвращает `None`, а `add` с тем же `ticket_id` проходит.
- Историю изменений и отдельную таблицу аудита не ведём.

### 5.3. SyncMetadata

Таблица `sync_metadata` хранит состояние синхронизации. Используется одна запись с `id = 1` (`SYNC_METADATA_ID`).

| Поле | Назначение |
|---|---|
| `id` | Первичный ключ, всегда `1` |
| `last_sync_time` | Время последней **успешной** синхронизации |
| `last_changed_at` | Наибольшее `changed_at` среди обработанных событий (с часовым поясом) |
| `sync_status` | `success` или `error` (константы `STATUS_SUCCESS`, `STATUS_ERROR` в `services.py`) |

Если записи ещё нет, курсором служит `2000-01-01`. В запрос к поставщику уходит **UTC-дата** `last_changed_at` в формате `YYYY-MM-DD`.

`last_sync_time` и `last_changed_at` обновляются только при успехе, в той же транзакции, что и события (раздел 8.3). При ошибке основная транзакция откатывается, а затем отдельной короткой транзакцией в `sync_status` записывается `error` (`_record_failure`); если не удалось и это, ошибка только логируется. Курсор при этом не меняется. Статуса «идёт» в БД нет: признак выполняющейся синхронизации — только флаг в процессе (раздел 8.5).

## 6. EventsProviderClient

Весь HTTP-код взаимодействия с Events Provider находится в классе `EventsProviderClient` (`app/events_provider.py`) на базе `httpx.AsyncClient`; все сетевые методы — `async`. Сервисы, маршруты и репозитории HTTP-вызовов поставщика не делают.

Компонент отвечает за:

- формирование запросов и добавление заголовка `x-api-key` в каждый запрос;
- таймауты: `DEFAULT_TIMEOUT = 30.0` секунд (задаётся и на клиенте, и на каждом запросе);
- разбор ответов через Pydantic-модели (`ProviderEvent`, `ProviderPlace`, `ProviderSeats`, `ProviderRegistration`, `ProviderUnregistration`, `EventsPage`);
- преобразование сбоев в исключения.

**Один клиент на процесс.** `get_shared_client()` создаёт клиент при первом использовании, `close_shared_client()` закрывает его при остановке приложения (`aclose()`). Им пользуются все маршруты и фоновый воркер, поэтому HTTP-соединения с поставщиком переиспользуются. Лимиты соединений `httpx` — значения по умолчанию (до 100 одновременных соединений); при большем числе одновременных запросов лишние ждут освобождения соединения в пределах таймаута, поведение под такой нагрузкой не измерялось.

### Поддерживаемые операции

| Операция | Запрос к поставщику | Результат |
|---|---|---|
| Страница событий | `GET /api/events/` с `changed_at=YYYY-MM-DD`, либо переход по готовому `next` | `EventsPage` (`results`, `next`, `previous`) |
| Свободные места | `GET /api/events/{event_id}/seats/` | `{"seats": [...]}` → список строк |
| Регистрация | `POST /api/events/{event_id}/register/`, JSON `{first_name, last_name, seat, email}` | `{"ticket_id": ...}` (непустой) |
| Отмена | `DELETE /api/events/{event_id}/unregister/`, JSON `{"ticket_id": ...}` | `{"success": true}` |

Пути поставщика содержат завершающий слеш; `event_id` подставляется с полным экранированием (`quote(..., safe="")`). Это не относится к маршрутам нашего API (раздел 9). Регистрация и отмена **не повторяются** автоматически; повторов запросов нет нигде.

### Политика редиректов

- Редиректы **не выполняются ни для одного запроса**: `follow_redirects=False` задан и на клиенте, и в каждом запросе (поэтому даже переданный извне клиент с другой настройкой не будет следовать редиректам). Ответ 3xx — это `ProviderRejectedError` с кодом ответа; адрес из `Location` в сообщение не попадает. Так API-ключ не может уйти за пределы `base_url`, в том числе при запросе страниц событий (в исходной синхронной версии для страниц событий редиректы выполнялись).
- Следствие: если у поставщика появятся легитимные редиректы на этих путях, запрос завершится ошибкой (502 у нашего API). Отвечал ли поставщик редиректами на используемых путях, неизвестно; это подтверждается только автотестами LMS после деплоя.
- Ссылка `next` не используется как есть: `_next_target` берёт из неё только путь и запрос, игнорируя схему и хост, и требует, чтобы путь был `/api/events/`; иначе — `ProviderUnavailableError`. Так ключ отправляется только на `base_url`, даже если поставщик вернул `next` с другим хостом, портом или схемой.

### Исключения и обработка ошибок

- `ProviderError` — базовый класс (не содержит API-ключ).
- `ProviderUnavailableError` — сетевая ошибка, таймаут (в сообщении только имя типа исключения), ответ, не прошедший разбор, неверный `next`, а также `success != true` при отмене.
- `ProviderRejectedError(status_code, body)` — ответ не 2xx. Тело (до 500 символов) сохраняется только для GET; для `register` и `unregister` тело **не сохраняется**, так как может содержать персональные данные.
- Ошибки не превращаются в пустые результаты: пустой список событий или мест возможен только если поставщик сам его вернул.
- Исключения клиента отделены от ошибок локальной БД; необработанный traceback клиенту нашего API не отдаётся.

### Неоднозначный результат

После таймаута или сетевой ошибки при `register`/`unregister` результат у поставщика **неизвестен**. Клиент ничего не повторяет и сообщает `ProviderUnavailableError`; сервис отвечает 502. Автоматической сверки состояния нет (раздел 18).

### Тестирование клиента

Клиент проверяется на `httpx.MockTransport`, без реального поставщика: `tests/test_events_provider.py` (страницы событий, `changed_at`, обработка `next`, HTTP-ошибки, сетевые сбои и таймауты для всех операций, некорректные тела ответов, редиректы 301/302/303/307/308 для всех операций, ровно один запрос для `register`/`unregister`, `aclose()`, неблокирующий event loop при медленном ответе, пагинатор). Дополнительно сервисные и маршрутные тесты проверяют ключ и персональные данные в ошибках на настоящем клиенте.

## 7. EventsPaginator

`EventsPaginator` отвечает за последовательный обход всех страниц событий поставщика. Он асинхронный: `__aiter__` — асинхронный генератор.

Пример использования:

```python
client = EventsProviderClient(...)

async for event in EventsPaginator(client, changed_at=cursor):
    # Обработка и сохранение события
    ...
```

Пагинатор должен:

1. Запрашивать первую страницу через `EventsProviderClient`.
2. Передавать `changed_at` при начальном запросе.
3. Получать массив `results`.
4. Возвращать события по одному через асинхронный итератор.
5. Переходить по URL `next`, пока он не станет `null`.
6. Завершать итерацию после последней страницы.
7. Пробрасывать ошибки клиента (HTTP-ошибка, ошибка разбора) наружу. Ошибка не должна восприниматься как нормальное окончание пагинации.

Страницы запрашиваются строго по одной и лениво: следующая — только когда потреблена предыдущая (параллельной загрузки страниц нет). Не предполагать, что поставщик возвращает фиксированное количество элементов на странице. Не вычислять следующую страницу самостоятельно, если поставщик предоставляет готовый `next`.

Ссылка `next` обрабатывается так, как описано в разделе 6 («Политика редиректов»): используются только путь и запрос, хост игнорируется.

Не выполнять HTTP-запросы из API-маршрутов для получения списка событий: пагинатор предназначен для синхронизации.

При тестировании клиент подменяется `AsyncMock` (или настоящий клиент на `MockTransport`); проверяются:

- одна страница;
- несколько страниц в порядке получения;
- пустой результат;
- завершение при `next = null`;
- передача курсора `changed_at`;
- обработка ошибки клиента;
- ленивость и остановка итерации потребителем.

Не добавлять лишние универсальные механизмы пагинации, если контракт поставщика их не требует.

## 8. Синхронизация событий

Синхронизация выполняется по ручному запросу `POST /api/sync/trigger` (раздел 8.5) и автоматически фоновым воркером (раздел 8.4). Оба пути вызывают одну функцию `sync_events`.

### 8.1. Первичная синхронизация

Если сохранённого курсора нет, используется `changed_at=2000-01-01`. Все страницы обходятся через `EventsPaginator`, события сохраняются в PostgreSQL.

### 8.2. Последующие синхронизации

Курсор следующего запроса — **UTC-дата** сохранённого `last_changed_at`, без прибавления одного дня: события граничной даты получаются повторно. Формат даты — `YYYY-MM-DD`.

Правила курсора (`_sync` в `app/services.py`):

- Новый `last_changed_at` — максимум `changed_at` среди обработанных событий, но не меньше уже сохранённого (курсор не откатывается назад; тест `test_cursor_never_moves_back`).
- Повторно полученные события обновляются через upsert по внешнему `events.id` (`session.merge`), дубликатов нет.
- Если синхронизация не получила ни одного события, курсор не изменяется.
- Ошибка (HTTP, разбор, сохранение) не считается нормальным окончанием пагинации: транзакция откатывается, курсор остаётся прежним, `sync_status = error`. Повторный запуск безопасен благодаря upsert.
- Поставщик не передаёт удалений: события, исчезнувшие у поставщика, локально не удаляются.

### 8.3. Сохранение событий

Для каждого события из `EventsPaginator`: проверка и разбор через `ProviderEvent`, преобразование в плоскую строку (`to_row`), upsert по `id`. Часовой пояс значений без смещения принимается за UTC.

Все события выборки **и** обновление `sync_metadata` фиксируются **одним `commit`** в конце: при ошибке на любом шаге откатывается и то и другое (тест `test_save_error_keeps_cursor`). Постраничных коммитов нет.

### 8.4. Фоновый запуск

`SyncWorker` (`app/sync_worker.py`) — `asyncio`-задача, которую `lifespan` создаёт при старте (`asyncio.create_task`). Бизнес-логику синхронизации воркер не дублирует: каждый запуск — прямой `await sync_events(...)` (`run_sync_once`), без потоков и `asyncio.to_thread`. На каждый запуск создаётся собственная `AsyncSession` (закрывается при успехе, ошибке, остановке и отмене); `EventsProviderClient` — общий клиент процесса, запуск его не закрывает. Если `EVENTS_PROVIDER_API_KEY` не задан, запуск завершается `ConfigError`, и воркер действует как при любой другой ошибке (backoff); приложение при этом работает.

**Расписание.**

- Интервал — `SYNC_INTERVAL_SECONDS` (по умолчанию 24 часа, `0` — воркер не создаётся).
- Первое ожидание берётся из `sync_metadata.last_sync_time` (время последней **успешной** синхронизации; чтение асинхронное): свежая синхронизация назначает следующую на `last_sync_time + interval`. Если синхронизаций не было, срок прошёл или метаданные не читаются, первый запуск выполняется через 30 секунд после старта. Синхронизация при каждом старте без учёта `last_sync_time` не выполняется.
- Следующий запуск отсчитывается от **начала** предыдущего (`time.monotonic()`), поэтому длительность синхронизации не накапливается. Системное время используется только при расчёте первого ожидания по `last_sync_time`.
- Ошибка записывает только статус `error` и `last_sync_time` не меняет, поэтому после рестарта просроченная синхронизация повторяется через 30 секунд.

**Ошибки и backoff.** Любое исключение запуска (ошибка поставщика, БД, конфигурации) логируется одной строкой с типом исключения (трассировку без секретов пишет `_sync`) и не завершает цикл. Повтор через 5, 10, 20, 40 минут, далее не более 60 минут; задержка не превышает интервал. Успех сбрасывает backoff. Состояние backoff хранится в памяти и после рестарта начинается заново. `SyncAlreadyRunningError` (идёт ручная синхронизация) не считается ошибкой: шаг backoff не делается, провайдер не вызывается, срок пересчитывается по БД (не раньше чем через 30 секунд).

**Остановка.** `lifespan` вызывает `SyncWorker.stop()`:

1. Выставляется `asyncio.Event`: он прерывает ожидание расписания и виден работающей синхронизации. Та проверяет его между обработкой событий поставщика (параметр `stop` у `sync_events`), откатывает транзакцию и завершается `SyncStoppedError`; статус `error`, `last_changed_at` и `last_sync_time` при этом не меняются.
2. Если синхронизация не завершилась за 20 секунд (например, ждёт медленного поставщика), задача **отменяется** (резервный путь); отмена прерывает и ожидающий HTTP-запрос. Задаче дополнительно даётся 5 секунд на откат. Итого не более 25 секунд, меньше обычного периода завершения контейнера в 30 секунд.
3. `stop()` возвращает `True`, когда задача завершена. Только после этого `lifespan` закрывает общий клиент и engine. Если не помогла и отмена (`False`), клиент и engine остаются открытыми, пишется предупреждение.

`CancelledError` воркер не скрывает: отменённая задача получает состояние «cancelled». Если контейнер убит раньше (SIGKILL), PostgreSQL откатывает незавершённую транзакцию при обрыве соединения: курсор не повреждается, повтор безопасен благодаря upsert. Что происходит при отмене во время `COMMIT` — в разделе 3.

**Условия эксплуатации и ограничения.**

- Воркер работает внутри процесса приложения. Пока приложение остановлено, синхронизации нет: ежедневный запуск гарантируется только при работающем процессе. LMS иногда масштабирует Deployment до нуля; после следующего запуска просроченная синхронизация выполняется через 30 секунд.
- По проверке Kubernetes 22 октября 2026 года: один Deployment, 1 реплика, HPA нет, Dockerfile запускает один процесс Uvicorn без `--workers`. Постоянной гарантией это не считается.
- Поддерживается только один процесс и одна реплика (раздел 3, «Один процесс, одна реплика»). При нескольких репликах или процессах у каждого свой воркер и свой флаг: возможны до N синхронизаций за интервал и лишние запросы к поставщику; гонка вставки одного нового события завершает одну транзакцию ошибкой первичного ключа, которая откатывается и повторяется по backoff. Данные не портятся (проверено на PostgreSQL), но гарантий для такого режима нет. Распределённая блокировка (PostgreSQL advisory lock) не реализована.
- Стартовая синхронизация (через 30 с после запуска при пустой или просроченной БД) может пересечься с ручным `POST /api/sync/trigger`: тогда ручной запрос получает HTTP 409 (раздел 8.5). Контракт endpoint не менялся.
- Билеты с поставщиком отдельно не сверяются: в известном контракте нет эндпоинта списка билетов; свободные места запрашиваются по требованию (кэш 30 с). Фоновая синхронизация обновляет только события.

Схема БД применяется миграциями до старта Uvicorn (раздел 13); приложение таблицы само не создаёт.

### 8.5. Ручной запуск

`POST /api/sync/trigger` выполняет синхронизацию **до формирования ответа** (ответ уходит после её завершения; сама синхронизация асинхронна и не блокирует другие запросы) и возвращает HTTP 200 `{"success": true}`. Переход на HTTP 202 не реализован; автотест LMS допускает 200.

Защита от параллельного запуска: один флаг `_sync_running` внутри `sync_events` на уровне процесса, общий для ручного и фонового запусков (отдельного механизма у воркера нет). Проверка и установка флага идут без `await`, поэтому в одном event loop между ними никто не вклинится. Если синхронизация (в том числе фоновая) уже идёт, новый запрос не ждёт и получает HTTP 409; фоновый запуск при идущей ручной синхронизации пропускается без обращения к поставщику (тесты `test_manual_sync_is_refused_while_the_worker_syncs`, `test_background_sync_does_not_start_a_second_one_during_a_manual_sync`, `test_manual_trigger_over_http_is_409_while_the_worker_syncs`; те же сценарии на PostgreSQL).

Ошибки: недоступность поставщика, отказ или некорректный ответ → HTTP 502; не задан `EVENTS_PROVIDER_API_KEY` → HTTP 500. Любая ошибка логируется (трассировка без секретов), клиент получает короткое сообщение.

Ограничение: флаг действует только внутри одного процесса и **не защищает** от параллельной синхронизации в нескольких процессах или репликах. Распределённых блокировок (в том числе advisory lock) нет. Из-за upsert параллельный запуск не создаёт дубликатов, но может привести к лишним запросам к поставщику. Число реплик в LMS не подтверждено.

Время ручной синхронизации на реальном поставщике не измерялось отдельно; LMS-автотест проходит.

Для всех остальных маршрутов делегируется стандартный обработчик FastAPI, то есть остаётся **HTTP 422** (тесты `test_invalid_query_returns_422`, `test_other_endpoints_keep_422`). Требование 400 для этого маршрута вытекает из автотеста LMS.

### 9.3. Список событий

`GET /api/events`

| Параметр | Тип | По умолчанию |
|---|---|---|
| `date_from` | дата `YYYY-MM-DD`, необязательная | нет |
| `page` | целое ≥ 1 | `1` |
| `page_size` | целое ≥ 1 (верхней границы нет) | `20` |

Данные берутся только из локальной PostgreSQL; фильтрация и пагинация выполняются на уровне SQL (`LIMIT`/`OFFSET`). `date_from` превращается в `date_from 00:00:00 UTC` и применяется **включительно**: `event_time >= date_from`. Порядок стабилен: `event_time`, затем `id`. Некорректные query-параметры дают HTTP 422.

Ответ HTTP 200:

```json
{
  "count": 150,
  "next": "http://host/api/events?page=2",
  "previous": null,
  "results": [
    {
      "id": "event-uuid",
      "name": "Название мероприятия",
      "place": {
        "id": "place-uuid",
        "name": "Название площадки",
        "city": "Город",
        "address": "Адрес"
      },
      "event_time": "2026-01-11T17:00:00+03:00",
      "registration_deadline": "2026-01-10T17:00:00+03:00",
      "status": "published",
      "number_of_visitors": 5
    }
  ]
}
```

- `count` — число записей, подходящих под фильтр, до пагинации.
- `results` — события страницы; пустой массив, если записей нет (в том числе при `page` за пределами выборки). Пустая выборка — HTTP 200, не 404.
- `registration_deadline` может быть `null`.
- `seats_pattern` в списке **не возвращается**.
- `next` — `page * page_size < count`: URL запроса с `page=page + 1`, иначе `null`; `previous` — аналогично для `page - 1`, если `page > 1`, иначе `null`. Ссылки **абсолютные**: путь и остальные query-параметры (`date_from`, `page_size`, …) берутся из входящего запроса, `page` заменяется без дублирования (`request.url.include_query_params(page=…)`). Схема, хост и порт — из `PUBLIC_BASE_URL`, если он задан, иначе из `request.url`.

**HTTPS за reverse proxy.** TLS завершается на стороне LMS Ingress, приложение видит обычный HTTP, поэтому без настройки ссылки получали схему `http` (подтверждено на публичном сервисе: `next` и `previous` приходили с `http://`, хост верный). Решение — `PUBLIC_BASE_URL` (`app/config.py:get_public_base_url`, `main.py:list_events`): при заданной переменной схема и хост/порт ссылок подставляются из неё, а заголовки `Host` и `X-Forwarded-*` на ссылки не влияют (проверено тестами). Доверие к прокси через Uvicorn (`--forwarded-allow-ips`) не используется: CIDR Ingress неизвестен, а `*` позволил бы подделать схему. **Чтобы исправление заработало на LMS, переменную нужно задать в окружении деплоя** (`PUBLIC_BASE_URL=https://yuriynik156-events-aggregator.dev-2.python-labs.ru`); значение в Dockerfile не зашито. Без переменной поведение прежнее (ссылки по `request.url`, за HTTPS-прокси — с `http`). Остальные маршруты затронуты не были.

{

### 9.5. Свободные места

`GET /api/events/{event_id}/seats`

Ответ HTTP 200:

```json
{
  "event_id": "event-uuid",
  "available_seats": ["A1", "A3", "A4"]
}
```

`event_id` берётся из пути, `available_seats` — всегда массив (может быть пустым).

Порядок (`get_available_seats`):

1. Событие ищется в локальной БД; нет — 404.
2. Статус не `published` — HTTP 400 «Event is not published», к поставщику запрос не выполняется.
3. Соединение БД возвращается в пул (`commit` после чтения, раздел 3); затем проверяется кэш, при попадании ответ возвращается без запроса к поставщику.
4. Иначе `GET /api/events/{id}/seats/` у поставщика (без следования редиректам); ответ `{"seats": [...]}` кладётся в кэш.

Ошибки: поставщик ответил 404 — запись в кэше удаляется, ответ 404 «Event not found»; иной отказ, сетевая ошибка, таймаут или некорректный ответ — HTTP 502 «Events Provider request failed». Ошибка поставщика **не превращается** в пустой список и **не кэшируется**.

**Кэш (`SeatsCache`).** In-memory TTL-кэш, ключ — `event_id`, TTL 30 секунд (монотонные часы), защищён блокировкой на время операций с самим словарём; блокировка не удерживается во время запроса к поставщику, поэтому параллельные промахи могут по разу обратиться к поставщику. Кэшируются только успешные ответы, включая пустой список. Просроченная запись удаляется при чтении.

**Инвалидация:** после успешной регистрации и после успешной отмены (до локального сохранения), а также при ответе поставщика 404.

**Ограничения in-memory кэша:** он свой у каждого процесса, теряется при перезапуске, не ограничен по размеру (число ключей не превышает числа событий; записи удаляются только при чтении после истечения TTL или при инвалидации) и не согласован между репликами.

### 9.6. Регистрация билета

`POST /api/tickets`

Тело запроса (`TicketCreate`):

```json
{
  "event_id": "event-uuid",
  "first_name": "Иван",
  "last_name": "Иванов",
  "email": "ivan@example.com",
  "seat": "A15"
}
```

**Валидация Pydantic.** Все пять полей обязательны, строки обрезаются по краям и не могут быть пустыми. `email` проверяется по простому шаблону `^[^@\s]+@[^@\s.]+(\.[^@\s.]+)+$`, длина не больше 254 символов (`EmailStr` не используется, чтобы не добавлять зависимость; окончательное решение за поставщиком). Любая ошибка тела — отсутствующее или пустое поле, неверный email, невалидный JSON — даёт **HTTP 400** (не 422, см. раздел 9).

**Алгоритм (`register_ticket`):**

1. Событие ищется в локальной БД — нет: 404.
2. Статус не `published` — 400.
3. Если `registration_deadline` задан и текущее время (UTC) больше него — 400 «Registration is closed». Сравнение с дедлайном нестрогое: в момент дедлайна регистрация ещё открыта. Значение без часового пояса трактуется как UTC. Если дедлайна нет, регистрация считается открытой.
4. Место проверяется по `place.seats_pattern` (`seat_in_pattern`): шаблон вида `A1-1000,B1-2000` сравнивается диапазонами, без раскрытия. Место вне шаблона — 400 «Seat does not exist». Сегмент шаблона в неизвестном формате трактуется как «возможно» — решение за поставщиком.
5. Список свободных мест берётся через тот же `get_available_seats` (кэш или поставщик). Места нет в списке — 409 «Seat is not available», регистрация у поставщика не выполняется.
6. Один `POST /api/events/{id}/register/` с `first_name`, `last_name`, `seat`, `email`; без повторов и без следования редиректам.
7. После успешного ответа поставщика кэш мест события инвалидируется.
8. Билет сохраняется в БД (`TicketRepository.add` + `commit`, новая транзакция) только после подтверждения поставщика.
9. Ответ HTTP 201 `{"ticket_id": "..."}`.

Локальные проверки (шаги 2–5) — предварительный фильтр; окончательное решение принимает поставщик.

**Коды ошибок:**

| Ситуация | Ответ |
|---|---|
| Некорректное тело запроса | 400 |
| Событие не найдено (локально либо поставщик ответил 404) | 404 |
| Событие не опубликовано; регистрация закрыта; место вне шаблона | 400 |
| Место занято (по списку свободных мест) | 409 |
| Поставщик отказал с HTTP 400 (место занято и т. п.) | 409 |
| Прочий отказ поставщика, сеть, таймаут, некорректный ответ (в том числе при проверке мест) | 502 |
| Поставщик подтвердил регистрацию, но локальное сохранение не удалось | 500 с `ticket_id` в сообщении |

В ответах нет traceback, API-ключа и персональных данных; в логах — только идентификаторы.

**Внешний запрос и транзакция БД не образуют общей транзакции**, а соединение БД на время запросов к поставщику не удерживается (раздел 3). Если поставщик подтвердил регистрацию, а сохранение не удалось, транзакция откатывается, ошибка логируется (идентификаторы события и билета, без ФИО и email), клиенту возвращается 500 с указанием `ticket_id` и просьбой не повторять запрос. Компенсации (отмены у поставщика) и автоматической сверки нет. Если же поставщик не ответил (таймаут/сеть), реальный результат неизвестен: отвечаем 502 и локальную запись не создаём.

### 9.7. Отмена билета

`DELETE /api/tickets/{ticket_id}`

Ответ HTTP 200:

```json
{
  "success": true
}
```

**Алгоритм (`cancel_ticket`):**

1. Защита от параллельной отмены того же билета: идентификатор помещается в множество «в процессе» (проверка и добавление идут без `await`, блокировки не нужны); если он там уже есть — 409 «Cancellation is already in progress». Идентификатор удаляется из множества при любом исходе.
2. Поиск активной записи: `TicketRepository.get_active(ticket_id)` (`cancelled_at IS NULL`) — нет: 404 «Ticket not found». Чтение происходит уже под защитой, поэтому запрос, ждавший завершения другой отмены, видит билет отменённым и получает 404 без повторного DELETE.
3. Событие билета читается из локальной БД — нет: 404 «Event not found».
4. Если текущее время (UTC) не раньше `event_time` — 400 «Event has already started» (сравнение нестрогое: в момент начала отмена уже недоступна).
5. Один `DELETE /api/events/{id}/unregister/` с телом `{"ticket_id": ...}`; без повторов и без следования редиректам. Подтверждением считается `{"success": true}`; иной ответ — `ProviderUnavailableError` (502).
6. Кэш мест события инвалидируется.
7. В записи выставляется `cancelled_at` (UTC), `commit` (новая транзакция; соединение на время шага 5 не удерживалось). Запись остаётся в таблице.
8. Ответ HTTP 200 `{"success": true}`.

**Коды ошибок:**

| Ситуация | Ответ |
|---|---|
| Активного билета нет (в том числе повторная отмена) | 404 |
| Поставщик ответил 404 (событие или регистрация неизвестны) | 404; локальный билет остаётся активным |
| Событие уже началось | 400 |
| Параллельная отмена того же билета в этом процессе | 409 |
| Поставщик отказал с HTTP 400 | 409; билет остаётся активным |
| Прочий отказ, сеть, таймаут, неподтверждённый или некорректный ответ | 502; билет остаётся активным |
| Поставщик отменил, но локальное сохранение не удалось | 500 с `ticket_id` в сообщении |

**Ограничения защиты от параллельных запросов.** Множество «в процессе» существует только внутри одного процесса; при нескольких процессах или репликах два одновременных DELETE одного билета могут оба дойти до поставщика. Идемпотентность операции отмены у поставщика не подтверждена, поэтому её нельзя считать гарантированной. Ключ защиты — только `ticket_id`.

`ticket_id` — внешний идентификатор и может повторно выдаваться поставщиком после отмены (раздел 5.2): отмена всегда адресуется к активной записи.

### 9.8. Преобразование ошибок

Сводка по реализованным правилам `main.py`:

| Ситуация | Ответ |
|---|---|
| Неизвестное событие или билет | 404 |
| Тело `POST /api/tickets` не прошло валидацию | 400 |
| Query-параметры или тело других маршрутов не прошли валидацию | 422 |
| Нарушение локальных бизнес-правил (событие не опубликовано, регистрация закрыта, место вне шаблона, событие началось) | 400 |
| Конфликт: место занято, отказ поставщика с 400, параллельная отмена, параллельная синхронизация | 409 |
| Поставщик недоступен, отказал иным кодом, вернул некорректный ответ, таймаут | 502 |
| Не задан `EVENTS_PROVIDER_API_KEY`; поставщик подтвердил операцию, но локальное сохранение не удалось | 500 |

Ответы об ошибках не раскрывают traceback и секреты и не маскируются под пустой результат. Отказ поставщика с 404 сопоставляется с 404 (для мест, регистрации и отмены), с 400 — с 409.

## 10. Бизнес-логика и репозитории

Используется паттерн Repository (`app/repositories.py`) для доступа к PostgreSQL. Все методы репозиториев — `async` (на `AsyncSession`). Репозитории вызывают `flush`, но не `commit`; транзакциями управляют сервисы.

| Репозиторий | Операции |
|---|---|
| `EventRepository` | `get(event_id)`; `list(date_from, page, page_size)` → (события страницы, общее число), порядок `event_time, id`, `date_from` включительно; `upsert(data)` через `session.merge` |
| `TicketRepository` | `add(**fields)`; `get_active(ticket_id)`; `cancel(ticket, cancelled_at)` |
| `SyncMetadataRepository` | `get()`; `save(sync_status, last_sync_time, last_changed_at)` — поля курсора меняются только если значение передано |

Сервисы (`app/services.py`, все `async`) реализуют сценарии: `sync_events`, `get_available_seats` (с `SeatsCache`), `register_ticket`, `cancel_ticket`.

Репозитории не вызывают Events Provider API. Сервисы не знают о `HTTPException`, `Request` и других деталях FastAPI; для сообщения о результатах используются собственные простые исключения (раздел 3), которые `main.py` преобразует в HTTP-ответы.

Транзакции: сессия создаётся на запрос. Перед обращением к поставщику сервисы читают нужное, делают `commit` (возвращая соединение в пул) и записывают результат в новой транзакции; подробности и обоснование — раздел 3 («Транзакции и соединения»). Одну сессию не используют несколько задач.

## 13. PostgreSQL и миграции

Использовать Alembic для управления схемой базы данных.

Миграции должны включать создание необходимых таблиц и индексов.

Миграцией созданы индексы:

- идентификатора события;
- `event_time`, используемого при фильтрации и сортировке;
- `changed_at`, используемого при синхронизации;
- поиска билета по внешнему `ticket_id`: **частичный уникальный индекс** по `tickets.ticket_id` с условием `cancelled_at IS NULL` (раздел 5.2).

Первичный ключ `events.id` (внешний ID) предотвращает дубликаты событий при повторной синхронизации.

Не использовать SQLite в production. SQLite допустим для отдельных простых юнит-тестов, если они не требуют проверки специфичного поведения PostgreSQL. Для проверки транзакций и SQL-особенностей использовать PostgreSQL (раздел 11.5).

**Alembic и async.** Alembic остаётся синхронным (`alembic/env.py` создаёт обычный engine на `get_database_url()`, драйвер `postgresql+psycopg`) и запускается до Uvicorn, вне event loop; приложение использует тот же пакет `psycopg` в async-режиме. Поэтому отдельных URL в окружении не нужно, схема БД и миграции не менялись. Проверено на реальной PostgreSQL 16: `alembic upgrade head`, `current`, `check` («No new upgrade operations detected»), `downgrade base` и повторный `upgrade head`.

### Запуск миграций

Реализовано в Dockerfile: команда контейнера `sh -c "alembic upgrade head && exec uvicorn main:app --host 0.0.0.0 --port 8000"`. Контейнер работает под непривилегированным пользователем `appuser`. При ошибке подключения или миграции `alembic` завершается с ненулевым кодом, Uvicorn не запускается и приложение не обслуживает запросы без таблиц. В репозитории одна ревизия — `0001_initial_schema` (таблицы `events`, `tickets`, `sync_metadata`, индексы, внешний ключ, частичный уникальный индекс).

Ограничения:

- миграции не выполняются из обработчиков запросов и не запускаются приложением;
- при нескольких одновременно стартующих репликах отдельной координации миграций нет (advisory lock не используется); число реплик в LMS не подтверждено;
- параметры подключения: те же переменные, что использует приложение (раздел 4).

## 14. CI/CD и деплой

GitHub Actions должен выполнять проверку кода до отправки запроса на деплой в LMS.

### Фактический порядок

Workflow `.github/workflows/deploy.yml` запускается при push в `main` и состоит из трёх последовательных job:

1. **`check`**: checkout → Python 3.11 → `astral-sh/setup-uv` (uv 0.13.1) → `uv sync --locked` → `uv run ruff check .` → `uv run ruff format --check .` → `uv run alembic upgrade head` (на тестовой БД, как в контейнере) → `uv run pytest -rs`. Права: `contents: read`. В job поднимается одноразовый **service container `postgres:16`** (база `events_test`, тестовые учётные данные, не секреты: БД существует только на время job). Заданы `TEST_DATABASE_URL` и `REQUIRE_POSTGRES_TESTS`, поэтому PostgreSQL-тесты в CI выполняются и не могут быть незаметно пропущены.
2. **`build`** (`needs: check`): сборка образа для `linux/arm64` и `linux/amd64` и публикация в GitHub Container Registry с тегом `github.sha` (права `contents: read`, `packages: write`).
3. **`deploy`** (`needs: build`): POST-запрос на `https://lms.python-labs.ru/api/deploy-requests` с образом и репозиторием; ключ — секрет `LMS_API_KEY`. Деплой считается успешным только при HTTP 200; иначе job завершается с ошибкой и печатает тело ответа.

Ошибка Ruff, проверки форматирования, миграций или pytest останавливает `build` и `deploy`. Образ `build` и шаг `deploy` не менялись. Синтаксис и выражения workflow проверены `actionlint`; **фактический запуск в GitHub Actions ещё не выполнялся** (изменения не отправлены в репозиторий).

Секреты хранятся в GitHub Actions Secrets и секретах LMS; в workflow, Dockerfile и документе они не записаны.

Успешный деплой подтверждён результатом LMS-автотестов (раздел 11.6).

## 15. Безопасность и эксплуатационная надёжность

- В репозитории нет `.env`, `.idea`; `.env.example` содержит только демонстрационные значения.
- Входные данные проверяются через Pydantic; на других маршрутах остаётся стандартная валидация FastAPI.
- API-ключ поставщика передаётся только заголовком `x-api-key` на `base_url`: редиректы не выполняются ни для одного запроса к поставщику, хост ссылки `next` игнорируется (раздел 6). Ключ не попадает в сообщения исключений и логи.
- Персональные данные участников (имя, email) не логируются и не возвращаются в сообщениях об ошибках; тело отказа поставщика на регистрацию и отмену не сохраняется. Ответ 400 на невалидное тело регистрации не повторяет присланные значения.
- Пароль БД маскируется в представлении URL; ошибки конфигурации не содержат значений секретов.
- Таймауты 30 секунд на каждый запрос к поставщику; сетевые ошибки преобразуются в контролируемые 502.
- Билет подтверждается локально только после успешного ответа поставщика; отмена — тоже.
- Повторная синхронизация не создаёт дубликатов (upsert по `events.id`).
- Engine БД закрывается при остановке (`dispose_async_engine`), общий клиент поставщика — тоже (`aclose`), оба — только после остановки воркера. Каждый запрос получает свою сессию БД, она всегда закрывается.
- Защиты от параллельных операций (флаг синхронизации, множество отмен) и кэш мест — внутри одного процесса; отсутствуют Redis, распределённые блокировки, автоматическая сверка и гарантированная идемпотентность внешних операций.
- Аутентификации и ограничения частоты запросов в нашем API нет.

## 17. Правила дальнейших изменений

Этот раздел задаёт правила дальнейших изменений; этапы аудита и реализации A–D выполнены.

1. Перед изменением изучи фактический код, миграции, тесты и этот документ. Источник истины — реализация (раздел 1).
2. Вноси минимальные изменения; не переписывай рабочие компоненты без необходимости и не усложняй архитектуру ради формального соответствия документу.
3. Не делай предположений о контракте Events Provider, если их можно проверить по коду, тестам или материалам задания.
4. Не маскируй ошибки пустыми ответами, не отключай тесты и правила Ruff ради зелёного статуса.
5. Любое изменение сопровождай тестами и проверкой `uv run ruff check .`, `uv run ruff format --check .`, `uv run pytest`.
6. Не выводи и не коммить секреты и персональные данные.
7. При изменении поведения обновляй `DESIGN.md` в том же изменении и не оставляй планы в разделах о реализованной функциональности.
8. Коммит и деплой выполняются только после ревью.

**Главный критерий:** минимальное, надёжное и понятное решение, которое соответствует требованиям задания и проходит автотесты LMS.

## 18. Известные ограничения и возможные улучшения

### 18.1. Подтверждённые ограничения реализации

Следуют из кода и схемы БД.

1. **Фоновая синхронизация живёт внутри процесса приложения.** При остановке приложения (в том числе при масштабировании Deployment до нуля) она не работает; флаг и расписание не согласованы между репликами (раздел 8.4). При остановке сначала даётся 20 секунд на мягкое завершение, затем задача отменяется.
2. **Ссылки `next`/`previous` и HTTPS.** Корректная схема гарантируется только при заданной `PUBLIC_BASE_URL` (раздел 9.3); без неё за HTTPS-прокси ссылки будут с `http`. Префикс пути в `PUBLIC_BASE_URL` не поддерживается (валидация отвергает). Значение — один адрес на экземпляр: для нескольких публичных доменов не подходит.
3. **Защиты работают в рамках одного процесса:** флаг синхронизации, множество отмен «в процессе» и кэш мест не согласованы между несколькими процессами или репликами. Несколько workers Uvicorn или реплик не поддерживаются как гарантия (раздел 3).
4. **Неоднозначный результат у поставщика.** После таймаута или сети при `register`/`unregister` реальное состояние неизвестно; повторов и автоматической сверки нет. Состояние БД и поставщика может расходиться.
5. **Подтверждено поставщиком, но не сохранено локально.** В этом случае клиент получает 500 с `ticket_id`, компенсации нет. Если не сохранилась отмена, билет остаётся локально активным, а поставщик может позже выдать тот же `ticket_id` другому участнику — тогда сохранение новой регистрации упрётся в уникальный индекс активных `ticket_id` и также завершится 500. Требует ручного вмешательства.
6. **Отмена задачи во время локального сохранения после подтверждения поставщика** оставляет неизвестным, сохранено ли это локально (пишется запись ERROR с идентификаторами; компенсации нет). Аналогично отмена во время `COMMIT` синхронизации: данные согласованы, исход неизвестен, следующая синхронизация повторяет работу (раздел 3).
7. **Нет аутентификации** в нашем API: любой, кто знает `ticket_id`, может вызвать отмену.
8. **Нет обработки удалений:** события, исчезнувшие у поставщика, локально остаются.
9. **`page_size` без верхней границы**; простая проверка формата email.
10. **Ручная синхронизация отвечает после завершения:** её длительность на реальном поставщике отдельно не измерялась и может упереться в таймаут клиента (при этом она не блокирует другие запросы).
11. **PostgreSQL-тесты** пропускаются без `TEST_DATABASE_URL` (локально по умолчанию); в CI они обязательны, но фактический прогон CI ещё не выполнялся. Остальные тесты проверяют логику на SQLite. Версия PostgreSQL в LMS не подтверждена (проверка выполнена на 16.2).
12. **Нагрузочное тестирование не проводилось.** Неблокируемость event loop и независимость от размера пула проверены функциональными тестами (60 одновременных запросов к медленному поставщику), а не нагрузочным прогоном.
13. **Windows:** `psycopg` async не работает на `ProactorEventLoop`, который Uvicorn использует на Windows по умолчанию; для локальной разработки нужен `SelectorEventLoop` или Linux/WSL/Docker (раздел 3). В контейнере LMS (Linux) не проявляется.
14. **Редиректы поставщика не поддерживаются:** ответ 3xx — ошибка (раздел 6).

### 18.2. Неподтверждённые допущения

1. Формат внешних идентификаторов (хранятся как строки).
2. Включительность границы `changed_at`, точность и часовой пояс на стороне поставщика (поэтому курсор не сдвигается на день, а граничные события получаются повторно).
3. Идемпотентность `register` и `unregister` у поставщика (поэтому повторов нет).
4. Формат тел ошибок поставщика: реализация опирается только на HTTP-статусы 400 и 404.
5. Число реплик приложения в LMS (22 октября 2026 года наблюдалась одна, постоянной гарантии нет).

### 18.3. Возможные будущие улучшения (не реализовано)

- PostgreSQL advisory lock для фоновой синхронизации при нескольких репликах.
- Верхняя граница `page_size`.
- Сверка состояния после неоднозначных ответов поставщика; распределённые блокировки при нескольких репликах.
